Row 140 · 2026-09-30 · EVAL-15 · §137 A second blind test setdone

A second blind test set: blind_v2

Why we ran it

Every choice since the first blind set (row 100) rested on blind_v1, one generator written by one agent. Choices tuned on one set can overfit it.

What we tried

Another agent, given only the product brief and the item format, wrote blind_v2: its own merchant universe, bank styles and user types, more multi-purpose payees and new users; 1,500 items from 250 users. It was checked for leaks (no future rows, no category before it existed). The saved models read it on Modal, and every recent table was redone.

What we tried

CPU only, saved readings. Effort under the per-item rule on both blind sets for: decider alone; decider then the 35B for what it does not auto-file; decider × 35B on everything; and the previous encoder × decider → 35B system.

Row 142 · 2026-09-30 · EVAL-15 · §139 Routing the bigger model by historydone

Send the 35B only first-time payees

Why we ran it

With the system down to decider and the 35B (row 141), we looked at where blind_v2's misses are and whether the 35B helps or hurts in each place.

What we tried

CPU only. blind_v2 accuracy broken down by what decides each item, against the ideal reader. Then four routings: decider alone; 35B for what decider does not settle; 35B on everything; 35B only for payees the user has never filed.

How it did

blind_v2 systemtop-1 %first-time payees %user's own pattern (changed mind / weekday / trip) %effort W=1035B reads %
decider71.760.855.31.0840
decider → 35B (unsettled)75.268.046.51.00765
decider × 35B, first-time payees only73.368.557.51.00321

What we learned

  • The 35B's world knowledge overrides the user's own recent pattern on known payees: on blind_v2, changed minds fall from 44.2 to 5.4 and weekday rules from 65.4 to 56.8 when it is multiplied in.
  • Routing it to first-time payees only keeps the effort gain, protects habit cases, and cuts its share of transactions to 18 to 21%.
  • Recommended: decider for everything, the untrained 35B for first-time payees, YNAB's rule first unless the model is 0.2 more confident.

Questions it raised

  • Escalation still gains 2.6 points on blind_v2's known payees that routing leaves; combining the two was not tested.
  • Could a cheap merchant-kind line replace the 35B? Row 149.

Row 143 · 2026-09-30 · EVAL-15 · §140 Payee overlap between train and blinddone

How many blind-set payees did training already know?

Why we ran it

With two blind sets in use (row 140), the owner wanted overlap of payees between training and test recorded. Overlap is intended: real users share merchants, and a separate merchant database is meant to teach the model about certain payees.

What we tried

CPU only. Each blind query's normalised payee name checked against REAL-6's merchant catalogue and fact database, the Overture business-name pool and the kinds catalogue. Accuracy by group for the ideal reader, decider-4B, the untrained 35B and the routed system. Also wrote down how every split is held out.

How it did

What we learned

  • A fifth to a quarter of blind queries are payees training knew, mostly real chains; three quarters are novel.
  • On blind_v2 the known payees are multi-purpose chains filed several ways: knowing a payee is not knowing which of a user's categories this purchase belongs to.
  • Splits: every test set is held out by user, never by random transactions. blind_v1 has been the selection set in practice, blind_v2 informed some choices, so blind_v3 is kept untouched.

Row 144 · 2026-09-30 · EVAL-15 · REAL_DATA_SPEC.mddone

A written plan for testing on real YNAB data

Why we ran it

The owner asked for a real-data evaluation spec. The synthetic results (row 140's second blind set, row 143's split notes) had gone as far as synthetic data can; the next evidence has to be real histories.

What we tried

No model run. reports/REAL_DATA_SPEC.md sets out: the fields needed per transaction (including the raw statement string, YNAB's own suggestion at the time, whether the category was edited after confirming, and the memo, often the only clue for person-to-person payments); splits by user (70/15/15, by a hash of user id) with the last three months as queries and a sealed test split scored once; prompt construction as in the synthetic work; the measures (report card, rank score with lists of three, calibration by user group, anticipation, speed and cost); and harness steps.

What we learned

  • Splits are never by random transactions: that would leak a user's own naming and habits into training.
  • Some questions only real data can answer: how often users depart from a payee's usual category (and whether it is a slip or a change of mind), the share of first-time payees and new users, how varied category names are, and the value of W.
  • Real payee strings need resolving into one payee across users; the spec was later updated (2026-10-02) to say YNAB's data lacks clean merchant names.

Questions it raised

  • A dress rehearsal of the spec on REAL-7: row 162. Payee resolution: row 160 and row 171.

The owner: "instead of top 5, do top 3 measurements." Row 145's final check had used lists of up to five.

What we tried

CPU only, re-scoring saved readings (blind_v3 was not read again). Every list capped at three; the rank scale becomes first 0, second 1, third 2, not shown 10. On blind_v3 and the ordinary stream. Three became the scripts' default.

Row 147 · 2026-09-30 · DATA-7 · §143 Inferring payee kinds, zero-shotdone

Can a model tell what a user's category holds?

Why we ran it

Users' categories are personal ("Yum", "Mini humans"), so other users' names for a payee (row 124) do not map directly onto this user's list. A shared vocabulary of payee "kinds" could bridge them. The owner: "I also want to know if our model could infer a kind from a given set of categorized transactions or not."

What we tried

A canonical vocabulary of 41 payee kinds (plus "several kinds of spending" and "a person, trip or purpose"), mapped from each blind generator's own vocabulary. For each user category with a known meaning, the question "Which kind of spending does this user's category X hold?" after the user's history. Read zero-shot by untrained decider-4B, the untrained 35B and the recipe's decider-4B, on blind_v1 and blind_v2.

Example prompt

Transaction: 2025-06-12 | Google One | $2.99 | Thu
Category: Streaming & apps
...
Transaction: 2025-12-12 | AT&T Internet | $49.99 | Fri
Category: Phone & internet

A kindcat_v1 item (trimmed; the question is stored with the item): the options are the canonical kinds, answer "insurance".

Row 149 · 2026-09-30 · DATA-7 · §144 Canonical kind linesdone

Adding a "Kind:" line to the prompt

Why we ran it

Row 148 showed a payee's kind can be inferred 77 to 87% of the time; row 147 built the shared kind vocabulary. The question: does a kind line help the categoriser, and could it replace the 35B for first-time payees?

What we tried

A line such as "Kind: coffee shop or bakery" under every history row and the query, using either the generator's kinds (a merchant database that knows every payee) or a kind inferred by the 35B for the query. decider-4B with the other-users line read them without training (three seeds); a copy trained with kind lines read them too (two seeds). Also kind lines only for first-time payees, against routing them to the 35B (row 142). blind_v1 and blind_v2; blind_v3 untouched.

Example prompt

Categories: Ready to Assign, Mortgage, ... Takeout & dining, Coffee shops, Fun money, ... New York trip

Transaction: 2025-03-11 | Ticketmaster | $412.93 | Tue

Category: Fun money
...
Transaction: 2025-09-21 | 7-Eleven | $10.90 | Sun
Kind: gas station
Category: Takeout & dining

Transaction: 2025-09-22 | Northside Trampoline Park | $70.51 | Mon
Kind: entertainment (movies, events, games)
Category:

A blind_v1_kinds item (trimmed): a new local business whose kind line points to the user's "Fun money".

How it did

First-time payees, right 1st %blind_v1blind_v2effort W=10 (v1 / v2)
No kind lines59.960.80.622 / 1.084
Database kind line, first-time payees only76.868.00.543 / 1.043
Inferred kind line62.864.50.634 / 1.082

What we learned

  • Where a merchant database knows the payee's kind, one line for first-time payees is worth as much as the 35B, with no retraining and no large model.
  • Inferred kinds add little: one label carries less than the 35B's full distribution.
  • Kind lines on known payees do not help, and training with them costs the user's own patterns on blind_v2 (52.9 to 37.9).
  • Person-to-person payees barely move; memos are the missing signal.

Questions it raised

  • YNAB has no reliable kind database; what can the population's filings provide instead? Row 150.

Row 150 · 2026-09-30 · REAL-24 · §145 Inferring from population filingsdone

Payee profiles learned from a million users' filings

Why we ran it

The owner: "We don't have a reliable DB for the kind ... Let's try to infer what we can from our existing categorized transactions. We have about 1M users and about 1B transactions." Row 149 showed a kind database helps; this tries to build its equivalent from the population.

What we tried

A synthetic stand-in population: 2,000 extra users from blind_v2's world (2.6M transactions). Payees matched across users by a key built from the statement string (ai_experiments.payeekey: purity 0.98, coverage 0.83). Concepts learned with no vocabulary by clustering user categories by the payees filed under them (60 concepts such as "groceries / grocery"). Each payee gets a profile from earlier filings; the profile is mapped onto the test user's own categories. Used two ways: a no-model suggestion, and a mapped other-users line read zero-shot by decider-4B (three seeds).

Example prompt

Categories: Rent, Food, Nashville getaway, Coffee Shops, Public Transit, Phones, Maui vacation, Education, Entertainment, Shopping, Paychecks, Random
...
Transaction: 2025-09-28 | Publix | $119.45 | Sun
Category: Food

Other users file this payee as: Entertainment (20), Random (8), Coffee Shops (5)

Transaction: 2025-09-28 | Midtown Books | $42.08 | Sun
Category:

A blind_v2_mapped first-time payee (trimmed): the line names this user's own categories; the raw line would have read "Fun (3), Hobbies (2), Dining Out (1)".

How it did

blind_v2top-1 %first-time payees: 1st / top 3 %effort W=10
Raw other-users line (row 124)71.760.8 / 79.71.084
Mapped profile line70.856.2 / 77.61.111

What we learned

  • The population alone, with no language model, suggests the right category first for 52% of first-time payees (70% in the top three), where YNAB today has 0%.
  • The model maps other users' raw category names better than the clustering does (61% against 56%): some clusters mix unrelated things, and a wrong mapping is stated as the user's own category.
  • Multiplied into the model, the profile adds at most a point.
  • For real data: train on real filings so the population's knowledge sits in the weights, keep the raw line, and keep profiles as a no-model fallback.

Questions it raised

  • How well can payee strings be matched across users? Row 160; embeddings for payees and categories in row 157.
